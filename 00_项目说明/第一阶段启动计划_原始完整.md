### 独立运行环境

- 使用 Python 3.11，创建项目专用 Conda 环境，环境文件与缓存放在 F 盘。
- Windows 开发版以 PyTorch 2.8.0、官方 CUDA 12.6 构建作为初始安装组合，完成 GPU 前向、反向和有限值检查后锁定实际版本。
- 数据工具采用 NumPy、pandas、xarray、NetCDF、PyArrow、GeoPandas；测试使用 pytest。
- 下载、解压和清洗按文件或时间块处理，避免把全站全年数据一次装入内存。
- 本机初始训练使用 batch size 1、数据加载进程数 0，并记录峰值内存和显存。
- Linux 环境与 Windows 共用代码、配置和数据接口；正式 Mamba-3 依赖在 Linux GPU 环境验证后单独锁定。

## 三、数据下载、审计与固定划分

### 首批下载内容

已读取公开元数据，第一批文件体量如下，均采用固定记录与校验值：

| 顺序 | 数据 | 压缩体量 | 首阶段用途 |
|---|---|---:|---|
| 1 | `info.csv` | 约 1.2 MB | 建立候选站点索引 |
| 2 | `attributes.7z` | 约 19.1 MB | 地理属性整理与分层 |
| 3 | `shapefiles.7z` | 约 530.6 MB | 流域边界和空间匹配 |
| 4 | `Hourly2.zip` | 约 4.18 GB | 小时水位与来源流量 |
| 5 | `timeseries.7z` | 约 21.25 GB | 第一组流域平均气象 |

来源为 [Q/H 固定记录](https://zenodo.org/records/16729675)和[气象、属性及边界固定记录](https://zenodo.org/records/15066778)。首批压缩文件合计约 **26 GB**。

另一组 `timeseries_nonobs.7z` 约 35.66 GB。首阶段优先从第一组气象与 Q/H 的交集选站；审计发现气候或地貌覆盖不足时，再下载第二组。原网格气象、局地 DEM 和真实预报强迫在后续空间模型阶段加入。

工作盘先按 **150 GB** 做容量预算；实际解压前读取档案目录，根据展开体量重新核算。

### 下载器要求

已有下载脚本只能作为参考，新项目需要补齐以下行为：

- 支持文件清单预览、大小统计和剩余空间检查。
- 支持断点续传、重试和下载进度；服务端不支持续传时明确处理。
- 下载中的文件保留为 `.part`，校验通过后才标记完成。
- 验证官方 MD5，同时记录本地 SHA-256、文件大小、来源记录和获取时间。
- 保存元数据与许可证快照。
- 对已完成文件先校验，重复运行时跳过有效文件。
- 解压到独立目录，拒绝绝对路径和上级目录跳转。
- 网络失败、校验失败或解压失败均留下明确状态，不能继续训练半成品数据。

旧环境中的网络失败来自受限执行上下文；在获准访问后，公开元数据读取成功。正式下载前仍需进行小文件与续传检查。

### 从原始文件到可训练数据

先检查 20 个真实 NetCDF 的字段、单位、缺测值和时间语义，再形成版本化字段映射，随后批量处理。

数据准备需要完成：

1. **计量与时间统一**：UTC、小时时间支持、米制水位、立方米每秒流量、气象单位；站点 ID 保留前导零。
2. **水位质量审计**：有效覆盖、重复记录、异常标记、基准变更及稳定时期；负水位不直接判为错误。
3. **气象核查**：明确 P、T、PET 的真实字段与单位。缺少可验证 PET 时先完成来源和计算方法记录，不能用零值替代。
4. **属性白名单**：仅纳入独立可获得的地理属性。剔除观测流量派生指标；气候统计从许可历史气象重新计算。
5. **站点来源记录**：记录 Q 来源类别、基准证据、时间支持核验状态；未知项保留为未知。
6. **模型数据视图**：来源训练视图可以包含许可 Q；目标上下文视图物理移除 Q；未来 H 由评分程序单独读取。

标准化结果按站点分区存储，模型读取时再生成张量缓存。原始文件保留，所有派生文件能够由脚本重建。

### 100 站开发集与信息权限

先形成完整候选清单和水系关系，再选站、划分。

- 通过可验证河网拓扑追踪终端水系；流域边界和上下游重叠用于交叉检查。单纯按距离或随机站点划分不满足要求。
- 从候选水系中预留正式论文盲测组，第一阶段不运行该组的预测评分。
- 其余水系构成开发池，再选择约 100 站，覆盖面积、坡度、气候和水位记录差异。
- 开发池内部按完整水系划分训练、验证和开发评估组，站数比例以约 60/20/20 为目标，优先保证水系完整。
- 支持期有效 H 覆盖率初始门槛设为 80%；固定查询窗口有效 H 不足 90% 时不计入该窗口评分。所有排除原因留表。
- 样本不足时报告实际数量与原因，不用模型误差决定删站或补站。

第一阶段默认来源训练使用 2013 年 10 月至 2018 年 9 月，另准备至少两年气象预热；来源验证使用随后一个水文年。开发评估站沿用协议的 2019—2020 水文年支持期和 2020—2021 水文年未来检验期。

来源参考模拟流量按水系做三折交叉拟合；生成某水系参考流量的前端不得使用该水系 Q 训练。所有模型共用站点划分、样本索引和观测预算。

## 四、首阶段代码与实验交付

### 完整运行接口

统一提供以下命令能力：

`doctor → download → audit → split → prepare → train → predict → evaluate → report`

中文启动脚本调用这些接口。例如“运行数据审计”“训练静态模型”“运行无记忆消融”均由配置控制，不维护独立模型副本。

核心输入包括气象、地理属性、历史 H、缺测掩码和时间信息；预测输出包括：

- 站点、时间戳、实验与运行编号。
- 水位预测及概率成员；概率模型另给中位数和区间。
- 数据覆盖、模型版本和地方适配版本。
- 评估程序单独附加的观测与误差。

每次运行保存代码提交号、配置快照、数据与划分哈希、随机种子、环境版本、训练时间及资源消耗。

### 按顺序实现的模型

| 模型 | 首阶段实现 | 要回答的问题 |
|---|---|---|
| 持续性基线 | 使用许可支持期最后有效 H | 最简单参考水平是多少 |
| 区域 Q＋地方样条 | 来源训练 HBV，目标历史 H 拟合单调函数 | 低成本 H-only 方法能达到什么水平 |
| 直接水位 LSTM | 气象、地理、同预算历史 H 直接预测 H | 显式水文中间过程是否有收益 |
| ECHO 静态版 | 历史编码生成地方单调参考曲线 | 跨河流函数生成是否优于地方独立拟合 |
| ECHO 动态开发版 | 静态曲线＋变化驱动状态＋Gaussian 地方推断 | 动态记忆与地方适配是否提供增量 |

开发版默认采用两层、隐藏宽度 64 的 LSTM 上下文编码器；地理输入先使用经核验的标量属性。水文前端先以单节点 HBV 和守恒路由跑通，并保留多节点接口。

地方曲线保留 32 段正斜率结构，动态模块保留 16 个状态。概率链条先使用 32 维对角 Gaussian 跑通，不据此宣称已经验证复杂联合后验的收益。

正式 Mamba-3、GATv2、局地 Set Transformer 和条件样条流保留替换接口，首阶段不把未实现模块包装成已完成能力。

### 训练与消融顺序

依次完成水文预训练、静态响应训练、冻结静态后的动态增量训练，再运行 Gaussian 概率开发版。主模式完成历史适配后，不读取未来 H。

首阶段启用三组消融：

- **无地理**：核查独立环境属性是否有增益。
- **无记忆**：关闭动态状态，测量历史响应的增量。
- **资料预算**：比较 7、30、90 天和完整水文年，统一支持结束时刻与未来检验区间。

其他实验建立目录和说明，标为后续任务：空间降雨位置、联合成员重配、来源多样性、异构前端、真实预报、外部山区验证。目录存在不计作实验完成。

模型和最强神经基线最终运行三个固定随机种子。训练与停止规则只根据来源验证集决定，开发评估结果用于定位问题时须明确记为开发证据。

### 评估报告

首阶段报告必须包含全时段 MAE/RMSE、洪峰误差、到峰时差、缺测与失败情况；概率模型增加 CRPS、覆盖率及区间宽度。

事件阈值和合并规则在评分前固定；误差先在事件内计算，再站内汇总、跨站等权汇总。统计重采样以水系为单位。

图表包括站点与数据覆盖、逐站误差分布、相同未来下的模型比较、观测预算曲线，以及预先分层选定的 6—10 条洪水过程。报告保留表现较差的案例。

### 必须通过的测试

- **下载与数据**：中断恢复、重复运行、校验失败处理、单位转换、时区与时间支持、闰年 8,784 小时、缺测和基准分段。
- **信息权限**：目标及相连水系 Q 不进入来源训练；修改未来 H 不改变预测；目标 Q 派生属性不能通过白名单。
- **数学结构**：HBV 与路由水量闭合、非负储量、曲线及外推尾部单调、同输入状态收缩。
- **完整动态输出**：明确实现 `r(0)=0`，验证恒定 Q 下水位回到参考响应，而不只检查隐藏状态衰减。
- **推断一致性**：分块与连续推断一致、检查点恢复一致、同一地方函数重复查询一致。
- **整条流程**：一组小型合成数据与一组真实站点数据均可完成准备、训练、预测、评分和报告。

### 第一阶段最终验收

第一阶段完成的标准是：

1. 新环境可以按中文说明安装并重现小样例。
2. 数据来源、校验、站点选择和水系划分有记录。
3. 约 100 站开发流程运行完成，或明确报告未达到规模的具体数据原因。
4. 基线、静态 ECHO 和动态开发版使用相同观测预算与未来区间。
5. 关键测试通过，结果能够追溯到具体提交和配置。
6. 报告如实给出模型收益、无收益和失败情况。
7. 完成第一阶段 Git 提交、远程同步与版本标签。

预测精度不设预先保证值。第一阶段的作用是用真实证据确定：数据是否支撑任务、简单方法达到什么水平、ECHO 的哪些模块值得继续投入。
